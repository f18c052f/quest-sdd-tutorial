# 準備段階で分かったこと

spec に入る前の環境づくり（手順書の A〜D 段階）で見つかったこと。
**spec の記録ではないが、ガイドラインの修正材料になる。**

## 1. 「シーン・プレハブ・.meta を触らない」というルールが、正しい作業まで止めた

Unity のレンダリング設定を用意するのに、Unity が自分で作った `.meta` ファイルを
**中身を変えずに**コピーする必要があった。ルールはこれも禁止していた。

決めたこと: 「Unity が生成したファイルを、中身を変えずに扱うのは可（コピー・移動・削除）」
という但し書きを足した。**編集を禁じたかったのであって、存在を動かすことではなかった。**

## 2. 品質ゲートが、書いただけでは動いていなかった

わざと落ちるテストを1本置いて確かめたところ、**AI は止まらなかった。**
原因は3つあり、どれも「落ちるテストがあるのに素通りする」という壊れ方だった。

| 壊れていたところ | なぜ素通りしたか |
| --- | --- |
| PowerShell の設定 | エラーが出た時点でスクリプトが途中で死に、終了コードが 2 でなく 1 になっていた。AI が止まるのは 2 のときだけ |
| 文字コード | テスト名が日本語だったため返事が文字化けし、「結果が取れなかった」扱いになっていた |
| コンパイルの確認が無かった | コンパイルが落ちていると Unity は**前に通ったときのコード**でテストを走らせる。壊れたコードを書いたのに「2件中2件成功」と出た |

とくに3つ目。**テストが全部通っていても、コンパイルが落ちていることがある。**

気づき: **この種の仕組みは、壊れても何も起きない。**静かに全部通すだけなので、
壊れていること自体に気づけない。「設定した」と「動いている」は別で、
間を埋めるのはわざと落ちるテストを置いて確かめる作業だけ。

もうひとつ。ガイドラインはテストの合否で判定すると書いているが、**合否だけでは足りなかった。**
コンパイルが通っているかを別に確かめないと、テスト結果そのものが信用できない。

## spec: mosquito-core

人の表の mosquito-flight-core と mosquito-spawn-core を、roadmap で1つにまとめた spec（難易度の変化を外すと出現が小さすぎるため）。

層: L1 ／ ブランチ: `spec/mosquito-core`（最初は `spec/kosquito-core` と打ち間違え、閉じる前に直した） ／ 期間: 2026-10-05 〜 2026-10-05

| 項目 | 記録 |
| --- | --- |
| requirements.md 行数 | 147 / 250 |
| design.md 行数 | 517 / 800 |
| tasks.md 行数 | 104 / 300 |
| タスク数 | 8（1、2.1〜2.3、3.1、3.2、4、5） |
| 実装コミット数 | 8（ほかに仕様だけのコミット 1、見出しタスクの完了 1、design の追従 1） |
| AI が「完了」と言ったのにテストが落ちていた回数 | 0 |
| `/kiro-validate-impl` の結果 | GO（EditMode 173/173。うち mosquito-core 122） |

参考: ステアリング3ファイルの合計は 291 / 400 行（product 67、tech 111、structure 113）。変化なし。

**自分で手を入れた箇所と、その理由**（L1 は AI、L2・L3 は自分、が原則。外れたら理由を書く）

- コードはなし。原則どおり AI が完成させた
- 要件の段階で、次のことを自分で決めた
  - 刺したあとの蚊：その場で消える（同じ蚊に何度も刺されない。枠が空いて次の蚊が出る）
  - 「漂う」段階は持たない。蚊は出現した直後から顔へ近づく
  - 刺された判定の秒数は、範囲を出ても 0 に戻さず**累積する**。「出たら 0 に戻す」だと、しゃがむ・顔を振るだけで刺されずに済む（ズルができる）と分かったため。防ぐ手段は撃墜だけにした
  - 数値はすべて仮の初期値（刺された判定 0.3m・2.0秒、出現範囲 水平 1.0〜2.0m・高さ ±0.5m、同時 3匹、間隔 2.0秒、接近 0.5m/s）
- design と tasks は `-y` で承認した（読み返しは生成後に行った）

**変更したシーン・プレハブと、Editor での確認内容**（L2 以降のみ。この spec では該当なし）

-

**引っかかったこと・ガイドラインとずれたこと**

- **承認の手順（2回目）**：spray-hit-core と同じく、要件を承認しないまま `/kiro-spec-design` を実行して止まった。`-y` で進めたが、「読み返してから承認」と「`-y` で一気に進める」の区別が手順の上で見えにくいのは変わらない
- **要件の質問がズレを見つけた**：「範囲を出たら秒数を 0 に戻すか」を聞かれ、外部設計の「とどまられると刺される」を文字どおり読むとズルができると気づいた。外部設計の文言と、意図（顔に近づけさせない判断）が食い違う箇所は、要件の質問でしか表に出なかった
- **brief の「漂う」が要件で消えた**：brief と roadmap には「漂う → 顔へ近づく」と書いてあったが、要件で外した。roadmap の説明文は spec を閉じるときに直した
- **後のタスクが前のテストを壊す**：tasks のレビュー（独立したサブエージェント）で、タスク 4 で刺された判定を入れると、出現・撃墜のテストの途中で蚊が刺して結果が変わると指摘された。「刺された判定を確かめるテスト以外は刺さない設定値を使う」という決まりを design と tasks に足した。同じレビューで、0.016 秒刻みは float の誤差で出現のタイミングがずれること（1/64 秒に変更）、出現位置の式が design に無いことも見つかった。**タスクの順に作ると、あとの機能が前のテストの前提を崩す**ことは、タスクを分けた時点では見えなかった
- **RED が作れないタスク**：「刺したあとの蚊」の振る舞いは刺された判定から自動的に決まるので、単独のタスクにするとテストが先に落ちない。タスク 4 に統合した。上限の頭打ちも、撃墜（3.2）が無いと落ちるテストが書けないので 3.2 に移した。**「テストが先に落ちるか」でタスクの境目を決め直す**ことになった
- **RED の証拠**：新しい型・メンバーはコンパイルエラー（CS0246 / CS1061）、既存の型の振る舞いは実行時の失敗を証拠にした。各タスクで、実装後にわざとコードを壊してテストが落ちることも確かめた（ミューテーション確認）
- **テストで区別できない分岐**：撃墜済みの蚊への `Down()` の状態チェックは、撃墜した蚊が一覧から外れるので通らない防御になり、テストでは検出できなかった。「距離ちょうど 0.3m」のテストも float の誤差で許容誤差の有無を区別できず、0.300005m のテストを足して区別した
- **design と実装のずれ**：撃墜のテストを `MosquitoSwarmTests.Hit.cs` に分けたため、design の File Structure Plan と実際が食い違った。`/kiro-validate-impl` で見つけ、design を実装に合わせた
- **タスク単位のレビューを省いたタスク**：タスク 5（網羅の点検）はコードの変更が無かったので、レビューを省いて最終検証に任せた
- **ブランチ名の打ち間違い**：`spec/kosquito-core` で作業を始め、閉じる前に `git branch -m` で直した。spec 名とブランチ名の一致を機械で確かめる仕組みは無い

## ガイドラインへの提案

守れなかったルールのうち、**ルールの方を直すべき**と判断したものを書く。
ガイドライン第1章のとおり、まず「①機械が止める」にできないかを検討する。
「②人間の鉄則」は5つから増やさない。

| ガイドラインの箇所 | 現状 | 提案 | 区分（①機械／②鉄則／③目安） |
| --- | --- | --- | --- |
| 第8章（品質ゲート） | テストの合否で判定する、と書いてある | 合否だけでは足りない。**コンパイルが通っているかを別に確かめる**手順を足す。落ちていると前に通ったコードでテストが走り、全部成功と出る | ①機械 |
| 第8章（品質ゲート） | 仕組みを入れる手順はあるが、動作確認の手順が無い | **わざと落ちるテストを置いて本当に止まるかを確かめる**手順を必須にする。壊れても静かに全部通すため、確認しないと気づけない | ②鉄則 or ③目安 |
| 第1章（機械が止める） | シーン・プレハブ・`.meta` の編集を禁じている | 「編集」と「コピー・移動・削除」を分ける。後者まで禁じると正しい作業が止まる | ③目安 |

## このハンズオンの前提そのものへの気づき
