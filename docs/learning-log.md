# 準備段階で分かったこと

spec に入る前の環境づくり（手順書の A〜D 段階）で見つかったこと。
**spec の記録ではないが、ガイドラインの修正材料になる。**

## 1. 「シーン・プレハブ・.meta を触らない」というルールが、正しい作業まで止めた

Unity のレンダリング設定を用意するのに、Unity が自分で作った `.meta` ファイルを
**中身を変えずに**コピーする必要があった。ルールはこれも禁止していた。

決めたこと: 「Unity が生成したファイルを、中身を変えずに扱うのは可（コピー・移動・削除）」
という但し書きを足した。**編集を禁じたかったのであって、存在を動かすことではなかった。**

## 2. 品質ゲートが、書いただけでは動いていなかった

わざと落ちるテストを1本置いて確かめたところ、**AI は止まらなかった。**
原因は3つあり、どれも「落ちるテストがあるのに素通りする」という壊れ方だった。

| 壊れていたところ | なぜ素通りしたか |
| --- | --- |
| PowerShell の設定 | エラーが出た時点でスクリプトが途中で死に、終了コードが 2 でなく 1 になっていた。AI が止まるのは 2 のときだけ |
| 文字コード | テスト名が日本語だったため返事が文字化けし、「結果が取れなかった」扱いになっていた |
| コンパイルの確認が無かった | コンパイルが落ちていると Unity は**前に通ったときのコード**でテストを走らせる。壊れたコードを書いたのに「2件中2件成功」と出た |

とくに3つ目。**テストが全部通っていても、コンパイルが落ちていることがある。**

気づき: **この種の仕組みは、壊れても何も起きない。**静かに全部通すだけなので、
壊れていること自体に気づけない。「設定した」と「動いている」は別で、
間を埋めるのはわざと落ちるテストを置いて確かめる作業だけ。

もうひとつ。ガイドラインはテストの合否で判定すると書いているが、**合否だけでは足りなかった。**
コンパイルが通っているかを別に確かめないと、テスト結果そのものが信用できない。

## ガイドラインへの提案

守れなかったルールのうち、**ルールの方を直すべき**と判断したものを書く。
ガイドライン第1章のとおり、まず「①機械が止める」にできないかを検討する。
「②人間の鉄則」は5つから増やさない。

| ガイドラインの箇所 | 現状 | 提案 | 区分（①機械／②鉄則／③目安） |
| --- | --- | --- | --- |
| 第8章（品質ゲート） | テストの合否で判定する、と書いてある | 合否だけでは足りない。**コンパイルが通っているかを別に確かめる**手順を足す。落ちていると前に通ったコードでテストが走り、全部成功と出る | ①機械 |
| 第8章（品質ゲート） | 仕組みを入れる手順はあるが、動作確認の手順が無い | **わざと落ちるテストを置いて本当に止まるかを確かめる**手順を必須にする。壊れても静かに全部通すため、確認しないと気づけない | ②鉄則 or ③目安 |
| 第1章（機械が止める） | シーン・プレハブ・`.meta` の編集を禁じている | 「編集」と「コピー・移動・削除」を分ける。後者まで禁じると正しい作業が止まる | ③目安 |
