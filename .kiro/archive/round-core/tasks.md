# Implementation Plan

各タスクはテストを先に書き、落ちることを確かめてから実装する。完了の根拠は Stop フック（EditMode）の終了コードと Test Runner の結果だけとする（tech.md 禁止事項 5）。
新しい型・メンバーのテストはコンパイルエラーを、既存の型の振る舞いのテストは実行時の失敗を RED の証拠にする。実装前から通るテストは「回帰の確認」と書き、RED の証拠にしない。回帰の確認は、実装後にわざとコードを壊して落ちることを確かめる（ミューテーション確認）。

並行実行（P）は付けない。離脱判定の式（タスク 4.1）はファイルも規則も他のタスクと重ならないが、テストはすべて1つのアセンブリに入る。他のタスクがコンパイルエラーの RED にある間は 4.1 のテストが走らず、Stop フックの結果もどちらのタスクのものか分けられないため。

テストの決まり（design.md「Testing Strategy」）:
- 定位置とプレイヤーの位置には原点以外（例 (0.5, 1.2, -0.3)）を使い、定位置を差し引き忘れる誤りを検出する
- 仮の初期値の設定値は（60秒、1.0秒、0.5m、0.4m）。それ以外の組として（10秒、0秒、1.0m、1.0m）と（2.5秒、0.25秒、0.75m、0.25m）を使う
- 時間を細かく刻むときは 1/64 秒（float で誤差なく表せる）を使う
- 許容誤差（1e-5 秒、1e-5m）は、境界からその内側にずれた値（例 59.999996 秒、0.499995m）のテストで固定する。ちょうどの値のテストだけでは、許容誤差を消しても落ちないため
- 撃墜・刺されの知らせはタスク 3 で入る。それより前のタスクのテストは知らせを使わずに書き、撃墜数・スコアが 0 以外になる場面はタスク 3 で確かめる

## Implementation Notes
- Unity の Editor を開いたままのとき、テストは `unity command run_tests --mode EditMode --result-only` で走らせる（JSON の Summary.Failed で判定する）。コンパイルは `unity command recompile` のあと `recompile_status` が `up_to_date` になるまで待つ。テスト名・メソッド名は数字で始められない（`得点0…`、`撃墜1…` のように始める）
- 2.1・4.2: `Round.RequestStart` の「残り時間・撃墜数・スコアの初期化」と「警告なしから始める」は、テストでは区別できない防御のコード（待機では初期値、警告は結果に入るときに消えている）。tasks の方針どおり書いてある
- 2.3: 受付待ちの経過秒数は結果に入るとき 0 にする。残り時間を超えた分は数えない（回帰の確認テストで固定。数えるように壊すと落ちることを確かめた）
- 2.3 の撃墜数・スコアの初期化と 2.2 の保持は、スコアが入るタスク 3 のテストで確かめた
- 4.2: 離脱警告が出たまま結果に入る・待機へ戻るテストが、警告を消し忘れる誤りを捕まえる。ミューテーション確認は (a) 結果に入るとき警告を消さない、(b) 直前の警告を無視する、(c) `UpdateStray` が残り時間を変える、の3つで落ちた
- 5: 点検だけでコードの変更はない。公開メンバー（`RoundRules` の生成と4プロパティ、`StrayJudge.ShouldWarn`、`Round` の生成・`Rules`・`Phase`・`RemainingTime`・`DownedCount`・`Score`・`HomePosition`・`IsStrayWarning`・`RequestStart`・`Advance`・`NotifyDowned`・`NotifyBitten`・`UpdateStray`）のすべてに1本以上のテストがあり、境界5ケース（残り時間ちょうど 0・受付待ちちょうど・警告を出す距離ちょうど・警告を消す距離ちょうど・0 点で刺される）と許容誤差の4ケース（59.999996 秒・0.999995 秒・0.499995m・0.399995m）も固定されている。コードの差分がないので、タスク単位のレビューは行わず、最終の `/kiro-validate-impl` に任せた
